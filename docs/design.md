# 설계 확정 문서 — 포켓몬 카드 배틀

> 기획서(`docs/plan.md`)의 열린 질문을 전부 확정한 문서. 구현은 이 문서를 정본으로 따른다.
>
> **v2 (기술·턴제 도입)** — 초판은 "카드 1장 = 즉시 승패"였으나,
> 포켓몬의 **기술을 골라 가며 쓰러질 때까지 싸우는** 방식으로 확장했다.
> 바뀐 지점은 §1, §4, §5, §7. 히든 정보 원칙(§6)은 오히려 층이 하나 늘었다.

## 1. 라운드 구조 (확정)

6라운드. **각 라운드 = 1:1 턴제 전투** 이고, 한쪽이 쓰러지면 라운드가 끝난다.
6라운드 후 승수가 많은 쪽이 이긴다.

```
라운드 하나의 생애
  selecting  손패 6장 중 내보낼 포켓몬 선택   (상대 손패·선택 모두 비공개)
    ↓ 양쪽 제출
  battling   턴제 전투                      (여기서 처음 서로의 포켓몬이 공개)
    ↓ 한쪽 HP 0  또는  30턴 초과
  라운드 종료 → 다음 라운드 or 게임 종료
```

- 내보낸 포켓몬은 라운드가 끝나면 **손패에서 사라진다** (승패 무관, 1회용).
  그래서 6라운드에 손패 6장이 정확히 소진된다.
- 라운드가 무승부면 양쪽 다 승수를 얻지 않는다. 최종 승수가 같으면 게임 전체가 무승부.

**왜 "6마리 팀 배틀"이 아니라 라운드제인가**: 팀 배틀로 가면 교체 전략·상태 이월이 붙어
스코프가 크게 늘고, 무엇보다 **"상대 손패를 모르는 상태에서 무엇을 낼 것인가"** 라는
이 프로젝트의 교육 축(히든 정보)이 첫 판에 다 공개되며 사라진다. 라운드제는 그 축을 6번 반복한다.

## 2. 로스터 — 40마리 (확정)

1세대 중간~최종 진화형 40마리. **전설 제외**(스탯 밸런스가 튀어서 딜링 확률 설계가 무의미해짐).

명단의 정본은 `backend/app/roster.py` 의 `ROSTER_DEX_IDS`.
시딩 스크립트는 도감 번호만 갖고 PokeAPI 에서 스탯·타입·스프라이트·기술을 긁는다.
티어는 **하드코딩하지 않고 BST 에서 계산**한다 (§3).

## 3. 티어 컷라인 (확정)

**BST(base stat total)** = HP + 공격 + 방어 + 특공 + 특방 + 스피드.

| 티어 | BST 조건 | 마릿수 | 딜링 가중치 | 카드 1장이 이 티어일 확률 |
|---|---|---|---|---|
| S | ≥ 520 | 11 | 1 | 12.1% |
| A | 470 ~ 519 | 15 | 2 | 33.0% |
| B | 420 ~ 469 | 10 | 3 | 33.0% |
| C | < 420 | 4 | 5 | 22.0% |

- 컷라인은 로스터 BST 분포(실측 385~600)의 골짜기에서 잡았다.
  경계: 아쿠스타 520(S) / 독파리 515(A), 두트리오 470(A) / 레어코일 465(B),
  텅구리 425(B) / 레트라 413(C).
- 낮은 티어일수록 가중치가 높아 잘 나온다. 손패 6장이면 S급이 평균 0.7마리.
- 두 플레이어의 딜링은 **서로 독립**이다. 같은 종이 양쪽에 나올 수 있다.
- 한 플레이어의 손패 안에는 같은 종이 중복되지 않는다(비복원 추출).
- `scripts/seed.py --show-distribution` 으로 분포와 확률을 눈으로 확인할 수 있다.

## 4. 전투 규칙 (확정)

### 4-1. 기술 선정 — 포켓몬당 4개

PokeAPI 에서 **레벨업 + 기술머신(TM/HM)** 으로 배우는 기술을 후보로 모은다.

**후보 필터** (`app/roster.py`)

| 조건 | 이유 |
|---|---|
| `damage_class` 가 물리/특수 | 변화기(상태이상·능력변화)는 구현하지 않는다 |
| 위력 10 ~ **110** | 상한이 핵심. 1세대 포켓몬이 배우는 위력 120+ 기술은 사실상 전부 **대가**가 붙어 있다 — 이판사판태클/플레어드라이브(반동), 솔라빔(차지 턴), 역린(연속기 후 혼란), 엄청난힘(능력 하락), 대폭발(자신 기절). 그 대가를 구현하지 않은 채 넣으면 "무조건 이거"가 되어 **기술 선택이라는 축이 통째로 사라진다** |
| 명중 ≥ 70 | 운에만 맡기는 기술 배제 |
| `meta.drain == 0` | 반동기·흡수기 제외 (역시 미구현) |

**선정 규칙**

1. **자속(STAB) 기술 1개**를 반드시 넣는다 — 자기 타입 중 기대 위력이 가장 높은 것
2. 나머지는 **서로 다른 타입**에서 가장 센 것으로 채운다
3. 그래도 모자라면 기대 위력순으로 채운다

**기대 위력 = 위력 × 명중률** 로 비교한다. 그냥 위력순으로 하면
눈보라(110/70)가 냉동빔(90/100)을 밀어내는데 기댓값은 77 vs 90 으로 오히려 손해다.

> **레벨업 기술만 쓰면 안 되는 이유**: 1세대 자력기 풀은 타입이 지독하게 좁다.
> 이상해꽃의 공격 자력기는 풀·노말 둘뿐이라 기술 4개가 풀 3 + 노말 1 이 된다.
> 타입 상성이 재미의 축인데 낼 수 있는 타입이 하나면 고를 게 없다.
> 기술머신을 포함하면 **40마리 전부가 서로 다른 4타입**을 갖는다(실측).

### 4-2. 능력치 환산 — 레벨 50

종족값을 그대로 쓰지 않고 정식 공식으로 레벨 50 능력치를 만든다 (개체값 31, 노력치 0).

```
HP    = floor((2*종족값 + 31) * 50/100) + 50 + 10   # = 종족값 + 75
그 외 = floor((2*종족값 + 31) * 50/100) + 5         # = 종족값 + 20
```

상수(+75, +20)를 바로 쓰지 않고 공식을 남겨 둔 건 레벨을 바꾸고 싶을 때
어디를 건드릴지 보이게 하려는 것.

### 4-3. 타입 상성 배율

18타입 상성표(6세대 이후)를 서버 상수로 둔다 (`app/type_chart.py`).
**기술 타입** 하나가 방어자 타입들에 대해 갖는 배율을 곱한다 — 0, 0.25, 0.5, 1, 2, 4.

(초판은 "공격자가 가진 타입 중 유리한 쪽"을 자동 선택했지만, 이제 기술을 직접 고르므로
그 추상화는 필요 없어졌다. `best_multiplier` 는 카드 선택 화면의 참고 표시용으로만 남는다.)

### 4-4. 데미지 공식

```
base = ((2 * 레벨/5 + 2) * 위력 * 공격 / 방어) / 50 + 2
최종 = floor( base × 자속 × 타입상성 × 난수(0.85~1.00) )
```

- 물리 기술이면 공격/방어, 특수 기술이면 특공/특방을 쓴다
- 자속(STAB) = 기술 타입이 자기 타입과 같으면 1.5배
- 상성이 0배면 데미지 0 (그 외에는 공식 끝의 `+ 2` 덕에 최소 2 언저리가 들어가
  라운드가 영원히 안 끝나는 일이 없다)
- 난수 폭 0.85~1.00 은 정식 시리즈와 같다

**난수는 인자로 주입한다**(`rng`). 안 그러면 데미지 테스트를 쓸 수 없다.

### 4-5. 명중 / 턴 순서

- 매 공격마다 `randrange(100) < 명중률` 로 명중 판정. 빗나가도 **PP 는 소모된다**
- 스피드가 빠른 쪽이 먼저 친다. 같으면 동전던지기
- **먼저 쳐서 쓰러뜨리면 상대는 반격하지 못한다** — 스피드가 중요한 이유

### 4-6. 발버둥 (PP 소진)

쓸 수 있는 기술이 하나도 없으면 **발버둥**만 쓸 수 있다.

- 위력 50, 물리, 명중 100, PP 무한
- **타입 상성 무시** (노말이지만 고스트에게도 통한다)
- 준 데미지의 **1/4 을 자신도 받는다** → 양쪽 동시 기절이 가능하고, 그건 무승부다

> 실제로는 거의 발동하지 않는다. 기술 4개 × PP 10~15 = 40회 이상인데
> 전투는 보통 2~5턴에 끝나기 때문. 교착 상황의 안전장치에 가깝다.

### 4-7. 기술의 그림과 이펙트

**PokeAPI 는 기술 이미지를 주지 않는다.** `/move/{name}` 응답에 sprite·image·icon 계열 키가
하나도 없다(확인함). 그래서 세 갈래로 나눠 처리한다.

| 필요한 것 | 출처 | 방식 |
|---|---|---|
| 타입 배지 | `/type/{name}` → `sprites` | **공식 이미지 존재.** 시딩해서 DB 에 URL 보관 |
| 기술 설명 | `/move/{name}` → `flavor_text_entries` | 한글 설명 존재. 툴팁에 표시 |
| 기술 이펙트 | — | **코드로 생성** (Three.js 파티클) |

**타입 아이콘은 두 종류를 다 받는다.** `sprites[세대][게임]` 구조에
`name_icon`(타입 이름이 적힌 가로 배지, 200×40)과 `symbol_icon`(정사각 심볼, 60×60)이 있다.
구세대엔 `symbol_icon` 이 없으므로 최신 세대부터 훑어 처음 나오는 걸 쓴다.

- 기술 버튼처럼 넓은 자리 → `name_icon`
- 손패 카드처럼 좁은 자리 → `symbol_icon` (118px 카드에 가로 배지 2개는 안 들어간다)

**이펙트는 `frontend/src/three/typeEffects.js` 에 타입 18종을 정의한다.**
스프라이트 빌보드로 3D 를 흉내낸 것과 같은 접근 — 에셋을 구하는 대신 코드로 만든다.

- `MODES` 11가지 분사 패턴: `burst` `projectile` `beam` `ground` `ring` `spiral`
  `shards` `rain` `implode` `sparkle` `drift`
- `EFFECTS` 18종: 타입마다 모드 + 색 2개 + 속도·중력·감속·수명·파티클 크기

예: 불꽃은 공격자→대상으로 날아가며 위로 뜨고(중력 +), 땅은 대상 발밑에서 솟았다 떨어지고(중력 −),
전기는 두 지점을 잇는 직선에 깔렸다 빠르게 사라지고, 악은 바깥에서 안으로 빨려든다.

배율에 따라 크기를 조절해 결과가 눈에 보이게 한다 — 2배 이상 1.35배, 0.5배 이하 0.7배,
0배 0.3배, 빗나감 0.45배.

> 파티클 **크기**는 `PointsMaterial` 에서 객체 단위 속성이라 하나의 `Points` 로는
> 타입마다 다르게 줄 수 없다. per-particle 크기를 하려면 `ShaderMaterial` 이 필요한데
> 예제엔 과하므로, 방출기 4개를 만들어 돌려 쓴다(동시 재생도 이걸로 해결된다).

### 4-8. 라운드 종료 판정

1. 한쪽 HP 0 → 상대 승
2. 양쪽 동시 HP 0 → 무승부
3. **30턴** 초과 → 남은 HP **비율**이 높은 쪽 승, 같으면 무승부

|---|---|---|

## 6. 히든 정보 규칙 — 이 프로젝트의 핵심 ★

> 서버는 **소켓별로 다른 페이로드를 만든다.** 브로드캐스트 금지.

기술·턴제가 들어오면서 숨겨야 할 층이 **세 겹**이 됐다.

| 단계 | 공개 | 비공개 |
|---|---|---|
| 카드 선택 | 상대 손패 **장수** | 상대 손패의 내용 전부, 상대가 무엇을 냈는지 |
| 전투 시작 | 상대 포켓몬, 그 스탯, **기술 목록** | 상대 기술의 **남은 PP** |
| 매 턴 | (양쪽 제출 후) 두 기술과 데미지 | 상대가 이번 턴에 고른 기술 |

- `deal` 은 각 플레이어에게 자기 패만 담아 개별 전송
- 상대가 카드를 냈을 때 나가는 건 `opponent_played` **빈 페이로드**뿐
- 상대가 기술을 골랐을 때 나가는 건 `opponent_move_selected` **빈 페이로드**뿐
- **남은 PP 는 끝까지 안 보낸다** — 정식 시리즈에서도 안 보이고,
  "같은 객체라도 보는 사람에 따라 다르게 직렬화한다"를 한 번 더 보여주는 지점이다
  (`Fighter.to_payload(private=...)`)

### 서버 검증

클라이언트가 보내는 건 의사표시뿐이고 서버가 전부 검증한다.

- `play_card` → 그 `card_id` 가 **이 플레이어의 손패에** 있는가
- `use_move` → 그 `move_id` 를 **이 포켓몬이 갖고 있고 PP 가 남았는가**
  (발버둥은 쓸 기술이 하나도 없을 때만 허용)

### 상성 배율도 서버가 계산한다

기술 버튼에 뜨는 ×2 / ×0.5 배지는 프론트가 계산하지 않는다.
서버가 `battle_start` / `turn_result` 의 내 기술마다 `effectiveness` 를 넣어 준다.
**타입 상성표를 프론트에도 두면 규칙이 두 군데 살게 되고, 한쪽만 고치면 화면과 판정이 어긋난다.**

## 7. WebSocket 프로토콜 (확정)

- 엔드포인트: `ws://<host>/ws/rooms/{room_code}?token={player_token}`
- 모든 메시지는 `{"type": "...", "payload": {...}}`
- `player_token` 은 방 생성/입장 REST 응답으로만 발급된다. 이것이 곧 신원.

### 7-1. Client → Server

| type | payload | 설명 |
|---|---|---|
| `ready` | `{}` | 준비 완료 토글. 양쪽 다 ready → 딜링 시작 |
| `play_card` | `{card_id}` | 이번 라운드에 내보낼 포켓몬. 라운드당 1회 |
| `use_move` | `{move_id}` | 이번 턴에 쓸 기술. 턴당 1회. `-1` 은 발버둥 |
| `rematch` | `{}` | 결과 화면에서 재대결 요청. 양쪽 다 요청하면 새 게임 |
| `ping` | `{}` | keepalive |

### 7-2. Server → Client

| type | 주요 payload | 설명 |
|---|---|---|
| `room_state` | `{room_code, status, round, board, you, opponent}` | 상태 변경 시마다 |
| `deal` | `{hand:[Card+moves], opponent_hand_count}` | **내 패만 전체**, 상대는 개수만 |
| `round_start` | `{round, deadline_ms, you_played}` | 포켓몬 선택 단계. `you_played` 는 새로고침 복구용(내 카드 id 또는 null) |
| `play_accepted` | `{card_id}` | 제출 승인 |
| `opponent_played` | `{}` | 상대가 냈다는 사실만 |
| `battle_start` | `{round, you:Side, opponent:PublicSide, hand_counts, max_turns}` | 전투 시작. 여기서 서로 공개된다 |
| `turn_start` | `{turn, deadline_ms, you_chose}` | 턴 시작 |
| `move_accepted` | `{move_id}` | 기술 선택 승인 |
| `opponent_move_selected` | `{}` | 상대가 골랐다는 사실만 |
| `turn_result` | `{turn, events:[Event], you:Side, opponent:PublicSide, auto_move}` | 턴 판정 |
| `round_result` | `{round, turns, winner, you, opponent, board, hand_counts}` | 라운드 종료 |
| `game_over` | `{board, result}` | 6라운드 종료 |
| `opponent_left` | `{}` | 상대 연결 끊김 |
| `error` | `{code, message}` | `INVALID_CARD` `INVALID_MOVE` `ALREADY_PLAYED` `ALREADY_CHOSEN` `BAD_STATE` `UNKNOWN_TYPE` `NO_ROSTER` |

## 8. DB 스키마 (확정)

Postgres 16. SQLAlchemy 2.0 (async, asyncpg).

### `pokemon` — 시딩된 로스터 캐시

`dex_id`(PK), `name`, `name_ko`, `types`(text[]),
`hp` `attack` `defense` `special_attack` `special_defense` `speed`(종족값),
`bst`, `tier`, `sprite_url`, `fetched_at`

### `moves` — 공격 기술 캐시

`id`(PK, PokeAPI move id), `name`, `name_ko`, `type`,
`damage_class`(physical/special), `power`, `accuracy`, `pp`, `flavor_ko`(한글 설명)

변화기는 저장하지 않는다. 실측 314개(그중 한글 설명이 있는 건 303개).

### `types` — 타입 18종 참조 데이터

`name`(PK), `name_ko`, `icon_url`(이름 배지), `symbol_url`(정사각 심볼)

아이콘 URL 을 기술 메시지마다 실어 보내면 WebSocket 페이로드가 쓸데없이 커진다.
거의 안 바뀌는 참조 데이터이므로 프론트가 `/api/types` 로 **앱당 한 번만** 받아 캐싱한다.

### `pokemon_moves` — 포켓몬이 가진 기술 4개

`pokemon_dex_id` + `slot`(0~3) 복합 PK, `move_id` FK

선정 규칙이 바뀌면 결과가 달라지므로 시딩 때 **통째로 지우고 다시 넣는다**.

### `rooms` / `room_players`

`rooms`: `id`(uuid PK), `code`(unique, 6자리), `status`, `created_at`, `finished_at`
`room_players`: `id`, `room_id` FK, `slot`(0/1), `display_name`, `player_token`(unique)
— `UNIQUE(room_id, slot)`

### `rounds` — 전적 기록

`id`, `room_id` FK, `game_no`(리매치 시 증가), `round_no`(1~6),
`slot0_dex_id` / `slot1_dex_id`, `slot0_hp_left` / `slot1_hp_left`,
`turns`, `winner_slot`(null = 무승부), `created_at`

**진행 중인 게임 상태는 DB 에 두지 않는다.** 인메모리(`GameManager`)에 있고,
DB 에는 끝난 라운드 결과만 적재한다 — 턴마다 DB 를 때리면 실시간 응답이 느려지고,
예제 스코프에선 서버 재시작 시 진행 중 게임이 날아가도 무방하기 때문.

## 10. 새로고침 복구

게임 도중 새로고침해도 이어서 할 수 있어야 한다. 재접속 시 서버가 현재 단계에 맞게 다시 보낸다.

- `selecting` → `deal` + `round_start`(내가 이미 낸 카드 id 포함) + 필요 시 `opponent_played`
- `battling` → `battle_start` + `turn_start`(내가 이미 고른 기술 id 포함) + 필요 시 `opponent_move_selected`

내 카드/기술 id 를 돌려주는 건 **자기 정보이므로 유출이 아니다**.
이게 없으면 새로고침한 사람이 또 낼 수 있다고 착각한다.

## 11. 구현하지 않은 것 (의도적으로 범위 밖)

- **상태이상·능력변화** (마비/화상/독, 칼춤 등) — 변화기를 통째로 제외한 이유
- **반동·흡수·차지·연속기** — 그래서 위력 110 초과 기술을 후보에서 뺐다
- **급소, 날씨, 특성, 지닌 물건**
- **교체** — 라운드당 1마리 고정
- 계정/로그인 — 방 코드 + 토큰으로 충분
- 랭킹/시즌, 3인 이상
