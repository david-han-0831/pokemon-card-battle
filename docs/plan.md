## 1. 게임 컨셉

**"포커 드로우식 1:1 배틀"**

방 코드 기반 매칭 → 서버가 각 플레이어에게 로스터에서 랜덤 6마리를 딜링 → 라운드마다 손패에서 1마리씩 동시에 내서 대결 → 6라운드 후 승수 많은 쪽 승리.

기존 "팀 빌드 직접 선택" 방식 대신 **랜덤 딜링**으로 가면서 팀 빌더 화면이 사라지고 구조가 단순해짐. 대신 티어(등급)를 딜링 확률에 반영해서 밸런스와 전략성을 확보.

---

## 2. 게임 흐름

1. **로비**: 방 생성 / 코드로 입장
2. **딜링**: 배틀 시작 시 서버가 양쪽에 6마리씩 랜덤 딜링 (상대 패는 개수만 노출, 내용 비공개)
3. **라운드 진행** (6라운드 반복)
   - 양쪽이 손패에서 1마리 동시 선택 → 제출
   - 서버가 타입 상성 + 스탯 비교로 판정
   - 승자 발표 → 사용한 포켓몬은 버려짐 (즉시 소모형)
   - 다음 라운드로
4. **결과 화면**: 최종 승수 비교, 승패 발표, 리매치 버튼

### 라운드 판정 방식: 즉시 소모형 채택
- 1라운드 = 즉시 승패 결정, 진 포켓몬은 버려짐
- "가위바위보 + 타입 상성" 느낌으로 규칙 단순, 계산 빠름
- (참고: HP 유지형은 상태 관리가 복잡해져 예제 스코프에는 과함 → 제외)

> ⚠️ **v2 에서 뒤집힌 결정.** 즉시 소모형은 한 판이 너무 얕아서,
> 라운드 안에서 **기술을 골라 가며 HP 가 0 이 될 때까지 싸우는 턴제**로 바꿨다.
> 라운드제와 "쓴 포켓몬은 버려진다"는 그대로 유지된다.
> 현재 규칙의 정본은 [`docs/design.md`](design.md) 다.

## 3. 포켓몬 로스터 & 티어

### 로스터 규모
1세대 진화 중간~최종형 위주로 **30~40마리** (전설의 포켓몬 제외 — 스탯 밸런스 튐 방지)

### 티어 분류 기준
PokeAPI의 `base_stat` 총합을 자동 계산해서 임계값으로 S/A/B/C 자동 분류
- 데이터 기반 로직으로 학생들에게 "왜 이 등급인지" 설명 가능
- 수동 매핑(Smogon 등 실제 경쟁 티어 참고) 대비 구현 간단

### 티어 반영 방식: 딜링 확률 가중치
- S급: 낮은 확률로 딜링
- C급: 높은 확률로 딜링
- 확정 슬롯 방식보다 랜덤성 있는 포커 컨셉과 부합

## 4. 기술 스택 매핑 (교육 포인트)

| 레이어 | 역할 | 학습 포인트 |
|---|---|---|
| PokeAPI → FastAPI | 초기 시딩 스크립트로 로스터 데이터(스탯·타입·기술·스프라이트) 긁어서 자체 DB에 캐싱 | 외부 API 연동 + 캐싱 패턴, 매번 호출하면 안 되는 이유 |
| FastAPI REST | 방 생성/입장, 로스터 조회 | Pydantic 모델, 비동기 라우팅 |
| FastAPI WebSocket | 딜링, 라운드 진행, 판정 로직, 히든 정보 필터링 | 실시간 통신, 서버 권위(anti-cheat) 개념 |
| React | 로비/배틀 UI, 소켓 클라이언트 | 상태관리, 실시간 데이터 반영 |
| Three.js | 배틀 스테이지(회전 발판) + 스프라이트 빌보드 연출 | 풀 3D 모델링 없이 게임 같은 느낌 내는 실전 트릭 |

**Three.js 관련 참고**: PokeAPI는 2D 스프라이트만 제공하므로, 풀 3D 모델 대신 **스프라이트 빌보드 + 파티클 이펙트** 조합으로 2.5D 연출. 3D 에셋 제작/라이선스 이슈 회피.

## 5. 핵심 교육 포인트 — 히든 정보 처리

이 구조는 **"히든 정보(상대 패)를 서버가 어떻게 다루는가"**를 가르치기 좋은 예제.

- 클라이언트에 상대 패 데이터를 절대 전송하면 안 됨 (개발자도구로 노출됨)
- 서버가 "내 패는 전체 전송, 상대 패는 개수만 전송" 방식으로 필터링
- WebSocket 실습에서 학생들이 흔히 놓치는 실수 → 좋은 반면교사 예제
